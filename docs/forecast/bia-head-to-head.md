# Next-word and fill-in-the-blank guessers: head-to-head

Generated by `pnpm bia:head-to-head` (tables), `pnpm bia:explain` (the worked example) and `pnpm bia:tune-chains`
(dev tuning, `bia-chain-tuning-dev.md`), 2026-10-12.

**Test split.** Every 10th verse of each English-source parallel pair is held out and never used for tuning.

- **Project sizes:** a project of size N trains on its first N translated verse pairs. It is scored on the held-out
  verses of the first 2,000-verse span (219–223 verses, the same verses for every N ≤ 2,000). "full" trains on every
  pair and scores every held-out verse.
- **Scoring:** each task scores 1,500 positions. Figures are top-1 / top-3 exact-word accuracy (%).
- **Confidence intervals:** a paired bootstrap that resamples whole test verses (2,000 resamples), so positions inside
  one verse are not treated as independent.

**Ten target languages.**

- **Low-resource (the tuning targets):** Nepali, Tok Pisin, K'iche', Chuukese.
- **Scripts without spaces between words:** Thai, Burmese, Japanese.
- **Agglutinative / polysynthetic:** Quechua, Turkish, Inupiatun.

## The default (`chooseGuesser` in `src/lib/forecast/bia-engine.ts`)

The rule uses only signals the app has at runtime: the task, whether the cell has a source verse, and how many
translated verse pairs the project has. It knows nothing about the language.

| task | no source verse (or no translated pairs) | with a source verse |
| --- | --- | --- |
| next word | per-distance chains | **BIA vote × chain weight, + 1 × source, × bigram weight** (any project size) |
| fill in the blank | BIA | BIA below 1,000 translated pairs; BIA + source (α = 2) from 1,000 |

**How the next-word guess with a source works:**

1. **BIA vote.** The rarest words already typed vote for the word found at the same distance from them in the
   project's validated verses.
2. **Chain weight on that vote.** Each candidate is multiplied by 1 + ln(1 + 300 · Σ_k P_k(w | word k back)/k). P_k is
   how often w appears exactly k = 1, 2, 3 places after each of the last three words (the per-distance chains). This
   is the "soft-sum" form. A word the chains have never seen in that slot keeps factor 1 instead of being zeroed.
3. **Source score**, from the project-learned lexicon: Σ over source words of IDF × Dice² × position weight, then ×
   the target word's IDF³.
4. **Mix:** chain-weighted vote / max + 1 × source / max.
5. **Bigram weight** × (1 + ln(1 + count(previous word → w))).

**Why the chains weight only the target-side guess.** If they weighted the mixed score (step 2 after step 4), a word
only the source proposes would be multiplied by the chain factor too. The harsh product form even zeroes it. A key
term the context never predicts, the reason the source exists, could then not surface mid-sentence. The ghost-text
journey checks exactly that ("Y Dios los bendijo diciendo:" → *Fructificad*). It passes unweakened with this recipe
and fails with the mix-stage variants.

**Lineage.**

- **The chain factor** comes from Daniel's per-distance forecasting: the first Python forecaster (TextGenerator,
  8f8f4a41, 2024-03) read the words n places after each word in the line, and BIA (3b676b1c, 2024-04) votes at each
  anchor's distance.
- **Its shape** reuses the bigram factor BIA already ships, 1 + ln(1 + count), with the multi-distance chain evidence
  inside instead of one bigram count.
- **The source term** is the project-learned lexicon from #1301 (AQU-1807).
- **What the 2024-09 TypeScript forecaster (V6, c42263ea) did:** it used only ±1 bigrams. Its reconstruction is the
  V6 column, and it is the weakest guesser here.

## What was tried (next word with a source)

| attempt | where measured | result |
| --- | --- | --- |
| BIA + source, bigram weight, α = 2 (the default before this change) | test | the baseline; trails plain BIA at 100–500 pairs (−2.2 at 100) |
| Chain *product* on the mixed score (`source + chains`) | test | +3.2 at 100 pairs, but fails the Fructificad check (offers "y la") |
| Adding the source after the chain product (α = 2) | test | collapses to source-only accuracy, 1–5 % top-1 |
| Soft chain forms on the mixed score (soft-product, soft-sum; scale 1–10,000; α 1–4) | dev | best dev means (soft-sum s=10 α=1: 18.02) but fail the Fructificad check (real e2e: "y díjoles") |
| Soft-lift (chain lift over the base rate) | e2e replay | passes only at a scale so small that the chains barely act |
| **Chains on the target side only, then source, then bigram** (soft-sum / soft-product / product; scale 3–1,000; α 0.5–3) | dev | **soft-sum s=300 α=1: 17.60, the best variant that passes the journey**; insensitive to scale (17.52–17.60 for s = 3…1,000) |
| Mixing weight α | dev | α = 2 → 1 is worth about +1.3 points; α = 0.75 scores 17.77 but loses the Fructificad check |
| Gate: plain BIA below a pair count | dev | the crossover is about 150–250 pairs. Any gate above 30 pairs fails the journey's 30-verse project (no empty-cell first word, no Fructificad). Daniel chose no gate. |

## Worked example: a young project (Tok Pisin, 250 pairs, Genesis 1:10)

This trace comes from `pnpm bia:explain -- --limit 250`. The values are the engine's own. The final ranking is checked
against `BiaEngine.suggestNext`.

| | |
| --- | --- |
| Source | "… God saw that it was good." |
| Typed so far | "… solwara god i". The next word is ***lukim*** ("saw"). |

1. **BIA vote.** 16 anchors (*solwara* 3 back, *kolim* 4 back, …). Top votes: *go* 2.16, *bin* 1.85, *mekim* 1.82, …
   *lukim* is not among them.
2. **Chain weight.**
   - *lukim*: P_1(lukim | i) = 0.020, P_2(lukim | god) = 0.101, P_3 = 0. The factor is 1 + ln(1 + 300 · (0.020 +
     0.101/2)) = 4.10.
   - *go*: P_1 = 0.074, P_2 = 0.013. The factor is 4.22.
   - Top after weighting: *go* 9.12, *mekim* 7.71, *tok* 7.24.
3. **Source.** "saw" ↔ *lukim*: 10 verses have both, 0 have "saw" only, 11 have *lukim* only, so Dice = 0.645. IDF is
   4.13 and the position weight 0.814 (word 18 of 22, cursor at 0.82), giving 1.40. Adding "that", "good" and "it",
   the total is 2.13. *go* gets 0.35. After × IDF³, *lukim* scores 86.4 (third, behind *amamas* and *gutpela*).
4. **Mix**, chained/max + 1 × source/max: *lukim* 1.41, *amamas* 1.27, *gutpela* 1.10, *go* 1.05.
5. **Bigram weight.** count(i → lukim) = 15 and count(i → go) = 56. Final ranking: ***lukim* 5.32**, *go* 5.28,
   *amamas* 4.05.

Result: the default says *lukim* and is right. Plain BIA says *go*, which is wrong. The margin is narrow; the source
carried it.

**Where it goes wrong.** Same project, Genesis 2:9, "… em diwai ___". The right word is *bilong*, and plain BIA
gets it. The source credits both *na* and *bilong* (both already typed, so ×0.25), and after the bigram weight *na*
edges ahead: 2.91 vs 2.80.

## BIA and the per-distance chains: related, not the same

| | BIA (`predictAt`) | per-distance chains (`chainProbability`, `backChainProbability`) |
| --- | --- | --- |
| Context used | The 15 rarest words, both sides of the blank, any distance | The nearest 3 words before (and, for infill, after) the blank |
| What is counted | At query time: one vote per distinct word an anchor lands on, decayed 1/\|d\| | Precomputed full counts of the word k places after/before each word → P_k |
| Combination | Votes summed | Product of experts Π_k (P_k + ε·P(w))^(1/k), or the soft forms (`ChainForm`) |
| Fills a gap from both sides | Yes | Yes since this PR (backward chains); it loses to BIA for infill |

**Are the ports faithful?**

- **BIA:** faithful, with documented deviations. `FAITHFUL_OPTIONS` reproduces the Python, which scores far lower.
- **Chains:** not a port of one Codex Editor version. They reconstruct the per-distance family described in "Lineage".

## Language-agnosticism

- **Shared by all three:** one tokenizer (`forecast-tokenize.ts`: NFC, `Intl.Segmenter`, Unicode classes,
  locale-independent folding), whole word forms, logical order for right-to-left scripts.
- **BIA and the chains:** need only target text and work from the first verse.
- **The source lexicon:** needs translated pairs, and its position weight assumes roughly monotone order. The new
  next-word default still never loses to plain BIA in any of the 10 languages, at any size, including the verb-final,
  space-free and agglutinative ones.
- **Agglutinative / polysynthetic:** every method is weak (Quechua 3–14 % next word, Inupiatun 5–18 %). Whole-word
  matching is the shared limit.

**Burmese (corrected).** The eBible Burmese text puts a ZERO WIDTH SPACE (U+200B) between every syllable. ICU's word
segmenter (78.2) treats ZWSP as a break, so every method sees syllables there. Without ZWSP, `Intl.Segmenter` gives
dictionary words (ဘုရားသခင်|သည်|…). The earlier note in this doc blamed ICU, which was wrong. Stripping ZWSP before
segmenting is a follow-up: it changes the caret offsets.

## The measurement is the one users get

- **One tokenizer:** the eval, the index, the caret parser, the lexicon and the thesaurus all share it.
- **Nepali under the old regex vs the new segmenter (current code):** full infill BIA 24.5 → 17.3, source 27.3 →
  21.1. Every method drops alike and their order is unchanged.

## Caveats

- **Determinism:** the eval sets are frozen, and reruns are identical (900/900 cells across two runs). The only
  spread is between languages and sizes.
- **What the CIs cover:** sampling of test verses within one Bible. They do not cover other translations, other
  genres, or real typing.
- **Tuning data:** dev tuning used the four low-resource languages only. The other six languages are checks.
- **Selection on the test split:** choosing between the target-stage and mix-stage recipes used the e2e journey, not
  test data. The test split was read only after the choice.
- **Source language:** the source is English (WEB) throughout.
