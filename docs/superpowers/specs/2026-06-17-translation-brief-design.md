# Translation Brief — Design

**Date:** 2026-06-17
**Status:** Approved (brainstorming → ready for implementation plan)

## Summary

A **Translation Brief** is a new project-level living artifact that encodes a
project's *skopos* (purpose) using the union of skopos-theory parameters
(Reiss & Vermeer 1984; Nord) and Paratext's project-standards fields. A project
lead authors it through a code-owned structured interview with per-field LLM
drafting help, optionally seeded from an uploaded document. It produces two
representations:

- **L1** — a compact (~150–250 word) practical, actionable summary, LLM-generated,
  injected into AI prompts on every call.
- **L2** — the full brief as an editable markdown document, pullable by the
  translation agent on demand.

The brief is **reference-only** in this iteration: it lives in the Living Memory
view and feeds the AI, but does **not** replace or modify the existing
AI Instructions (`systemPrompt`). Folding L1 into `systemPrompt` is explicitly
deferred.

## Background & research

**Skopos theory.** A translation is determined by its *skopos* — its purpose.
The artifact that encodes that purpose is the **translation brief**
(*Übersetzungsauftrag*). Nord's brief specifies: intended **text function(s)**,
**audience/addressees**, **time & place** of reception, **medium/channel**, and
the **motive** for the translation. How literal or adaptive the translation is
becomes subordinate to, and justified by, the brief.

**Paratext's brief.** "A statement of the standards for the project — which
source texts are used, and the specific audience and intended uses of the
translation," set at project start so the team works toward a common goal. Teams
also record source/base texts, target language & dialect, register, naturalness
vs. concordance, level of literalness (formal ↔ functional), and
denominational/theological constraints.

Sources:
- Schäffner, *Skopos theory* (overview)
- Reiss & Vermeer, *Towards a General Theory of Translational Action: Skopos Theory Explained*
- Paratext Project Plans tutorial — https://paratext.org/paratext-training/tutorials/project-plans/

**Existing building blocks (the brief slots in beside these, does not duplicate):**
- **AI Instructions** = `systemPrompt` in `project_settings` JSON, maintainer-gated,
  injected by `buildPrompt()` in `src/lib/completion/completion-service.ts`.
- **Rules-from-document** = two-pass LLM extractor → checkable rules
  (`src/lib/rules/rule-extractor.ts`, `src/components/RuleImportDialog.tsx`).
- **Living Memory** = `src/components/LivingMemoryPage.tsx` with authored
  `instruction`/`standard` entries + validated example pairs. No L1/L2 concept
  exists yet — that is net-new.

## Decisions (from brainstorming)

1. **Brief's role:** reference-only at first. L1 injected into AI prompts;
   AI Instructions box untouched. Re-evaluate folding into `systemPrompt` later.
2. **Authoring:** code-owned structured interview over the parameter schema,
   with a free-form "anything else" step at the end, and an optional document
   upload that pre-fills parameters via AI extraction.
3. **L1 lifecycle:** L1 is generated by an explicit "Generate summary" action
   (with a "summary out of date" nudge after edits). L1 is **always injected**
   into completion + agent prompts. The agent can additionally pull the full L2
   on demand via its `docs` tool.
4. **L2 storage:** a single editable markdown document (not per-section rich
   editing).

## Parameter schema (code-owned interview)

A fixed schema constant in code (deterministic — model is used only for drafting,
not for deciding structure). Each field has: stable `id`, `label`, `group`, and
`helperText` explaining the skopos/Paratext rationale.

**Group A — Purpose & audience (skopos / Nord):**
1. `purpose` — Purpose / skopos: why this translation exists; intended function(s)
   (evangelistic, liturgical, study, devotional, first Scripture, revision).
2. `audience` — Audience / addressees: age, literacy, churched/unchurched,
   bilingual with an LWC?
3. `useAndMedium` — Intended use & medium: read aloud / personal study / liturgy
   / audio / print / app / oral.
4. `motiveSponsor` — Motive & sponsor: commissioning body, denominational context.

**Group B — Standards (Paratext):**
5. `sourceTexts` — Source & base texts: original-language editions + front/model
   translations.
6. `targetVariety` — Target language & variety: dialect, orthography decisions.
7. `registerNaturalness` — Register & naturalness: formal/informal; naturalness
   vs. concordance.
8. `literalness` — Level of literalness: formal ↔ functional equivalence (spectrum).
9. `keyTerms` — Key terms & theological tradition: key-term strategy,
   denominational constraints, transliteration vs. indigenous terms.
10. `constraints` — Constraints & sensitivities: cultural/political/religious
    taboos, must-avoid renderings.
11. `qualityBar` — Quality bar: what "good/done" means.

## Data model

Reference-only, stored in the existing `project_settings` JSON blob (same pattern
as `livingMemoryEntries` / `systemPrompt`, maintainer-gated via
`patchProjectSettings`). New `translationBrief` key on `ProjectWideSettings`:

```ts
interface TranslationBrief {
  version: number          // bumped on each save
  updatedAt: string
  updatedBy: string
  parameters: Record<string, string>  // keyed by schema field id; schema lives in code
  freeformNotes: string               // the "anything else" step
  l2Markdown: string                  // full document, assembled from params + notes, editable
  l1Summary: string | null            // compact actionable summary, LLM-generated
  l1GeneratedAt: string | null        // L1 is "stale" when updatedAt > l1GeneratedAt
  l1ModelId: string | null
}
```

Staleness is derived, not stored: `isStale = l1GeneratedAt == null || updatedAt > l1GeneratedAt`.

## Authoring flow (`BriefBuilder`, maintainer-gated)

1. **Optional doc upload** — paste/upload an existing brief or notes → AI extracts
   into the fixed parameter schema (reuses the two-pass `rule-extractor.ts`
   pattern, but extracting into known field ids). Skippable.
2. **Structured interview** — step through the 11 fields. Each field shows its
   skopos/Paratext rationale as helper text, a textarea, and a "Help me write
   this" button → LLM drafts/refines from project context + already-answered
   fields.
3. **Free-form step** — "Anything else the AI should know?" → `freeformNotes`.
4. **Review → assemble L2** markdown (LLM-polished, editable) → "Generate summary"
   produces `l1Summary` (length-capped at generation).
5. **Save** → `patchProjectSettings({ translationBrief })`.

## AI consumption

- **L1 always injected:** a brief block added in `buildPrompt()` /
  `buildBatchPrompt()` in `src/lib/completion/completion-service.ts`, and into the
  translation agent's system prompt. Length-capped at generation time to protect
  the token budget.
- **L2 on demand:** the translation agent's `docs` tool gains a
  `translation-brief` resource returning `l2Markdown`, so it can consult the full
  brief for nuanced cases.

## UI placement

A new **"Translation Brief"** section at the top of `LivingMemoryPage.tsx`:
status (none / draft / complete), L1 preview, last-updated, "Edit brief" +
"Generate summary" with a "summary out of date" badge when L1 is stale.
**Read-only for non-maintainers** so PMs/owners can read the brief while
bilingual maintainers author it (aligns with the two-audiences model). The
`BriefBuilder` is a dialog (or nested route) launched from this section.

## Testing (intent, not just behavior)

- Staleness computation: L1 stale iff `l1GeneratedAt == null || updatedAt > l1GeneratedAt`.
- L1 length cap enforced at generation.
- Parameter round-trip serialization (save → load → identical).
- Doc→parameter extraction mapping (mock LLM).
- Prompt injection: `buildPrompt` includes the L1 block when present, omits it
  cleanly when the brief / L1 is absent; agent `docs` returns L2.
- UI: maintainer can edit vs non-maintainer read-only; stale badge appears after
  an edit.

## Out of scope (YAGNI)

- No brief version *history* (just a counter + timestamp).
- No folding into `systemPrompt` yet (reference-only).
- L2 is a single markdown doc, not per-section rich editing.
- No multi-brief-per-project; one brief per project.
