## Format-by-Format Detail

### XLIFF 1.2

**Verdict: clean round-trip for text content; `id` is regenerated, metadata degrades gracefully.**

- The exporter writes XLIFF 1.2 with `<trans-unit id="${c.group || c.id}">` and a matching `<note>` element.
- On re-import the parser assigns a fresh UUID as the cell `id` (the original `c.id` is not stored in the XLIFF output).
- `group` on re-import becomes the `<trans-unit id>` value (= the original `c.group`), because there is no enclosing `<group>` element in the exported file.
- `context` on re-import comes from `<note>`, which equals the trans-unit `id` (= `c.group`). So context and group are both the original group value after a round-trip.
- Special XML characters (`&`, `<`, `>`, `"`, `'`) are entity-escaped on export and transparently unescaped by the DOM parser on import — clean.
- Inline markup (XLIFF `<g>`, `<x>`, `<bpt>`, `<ept>`, `<ph>`, etc.) is stripped to plain text on import. Text content is preserved but structural tagging is lost. This is a known, documented limitation of the import parser (see `SWARM-TODO(import)` in `xliff.ts`).
- **Multi-segment units (XLIFF 2.0):** multiple `<segment>` children are concatenated with a space separator. The exporter produces only XLIFF 1.2, so this only affects re-import of externally sourced XLIFF 2.0 files.

### TMX 1.4b

**Verdict: clean for non-empty translation pairs; untranslated segments are silently dropped.**

- The exporter filters out cells where `c.translated.trim()` is empty — TMX is a Translation Memory eXchange format and has no concept of an untranslated source segment.
- For non-empty pairs: source, translated, and group/tuid survive cleanly.
- Special XML characters (`&`, `<`, `>`, `"`) are entity-escaped on export and unescaped on import — clean. Note: `'` (apostrophe) is NOT escaped by the TMX exporter's `xmlEscape()`, which is safe since TMX attribute delimiters use double-quotes.
- `group` survives via the `tuid` attribute: exporter writes `tuid="${c.group || c.id}"`; parser reads `tuid` back into `group`.
- Inline markup in `<seg>` elements is stripped to plain text on import (same as XLIFF).
- The `creationdate` timestamp in the TMX `<header>` is generated at export time — this is expected and not a fidelity concern.

### CSV

**Verdict: full round-trip for all tested cases including commas, double-quotes, and embedded newlines.**

- Exporter writes a header row `id,source,target` followed by one RFC-4180 row per cell.
- The parser recognises the `id`, `source`, `target` column names and uses the `id` column as `context`/`group`.
- RFC-4180 quoting correctly handles:
  - Fields containing commas: `"Hello, world"` → `Hello, world` ✓
  - Fields containing double-quotes: `"She said ""hello"""` → `She said "hello"` ✓
  - Fields containing embedded newlines (quoted): multi-line text survives ✓
- Empty-target cells are preserved: `original` is kept, `translated` is `""`.

### TSV

**Verdict: clean only for text without `"`, `\t`, or `\n`; three known lossy cases.**

1. **Double-quote in field values (corrupting):** The TSV exporter does not quote or escape `"` characters. The re-importer (RFC-4180 CSV/TSV parser) treats `"` as a field-quote opener, corrupting any row containing a `"` in source or target. **Workaround: use CSV format.**

2. **Tab characters in field values (normalised to space):** The exporter explicitly replaces `\t` with ` ` to protect the tab-delimiter structure. Any source/target containing a literal tab is flattened. **Workaround: use CSV format.**

3. **Newlines in field values (normalised to space):** The exporter replaces `\r?\n` with ` `. Multi-line source/target text is flattened to a single line. **Workaround: use CSV format.**

- Group/id column and empty-target cells survive correctly when no `"` is present.

### Plain Text (txt)

**Verdict: one-way export only — source text permanently lost.**

`exportPlainText` emits one line per translated cell. The source text is completely absent from the output. There is no inverse parser that produces a bilingual `TranslatableString[]` from a plain-text file. This format is appropriate for final deliverables but not for translator hand-off or re-import.

### Markdown (md)

**Verdict: one-way export only — source text permanently lost.**

`exportMarkdown` emits translated text with group-based HTML comment anchors (`<!-- group -->`). The source text is completely absent. While `extractMarkdownStrings` can parse Markdown into segments, the re-parsed `original` field would equal the translated content — the source is not recoverable. This format is appropriate for publication but not for bilingual exchange.

## Recommendation for Paratext/SIL Users

For lossless round-trip use **XLIFF** or **CSV**:

- **XLIFF** is the industry-standard CAT exchange format. Text content survives cleanly; inline markup is currently stripped (see `SWARM-TODO(import)` in `xliff.ts` for the upgrade path).
- **CSV** provides the simplest full-fidelity round-trip with no XML complexity, suitable for spreadsheet-based workflows.
- **TMX** is appropriate for exporting a finished translation memory but not for re-importing partial work (untranslated segments are dropped).
- **TSV** should be avoided when source or target text may contain `"`, tabs, or newlines.
