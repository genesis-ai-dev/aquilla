# First agent-browser run, 2026-09-08

Half-day experiment answering the 2026-09-03 call: can an agent walk our
smoke journeys through the real app, and what does it cost. Local stack
(`pnpm dev` on this branch, dev tip `01740eb5a`), agent-browser 0.27.0,
Chrome 153, one Claude Code session as the agent.

## Results

| Story | Cold run (agent reads snapshots) | Warm run (labels known, no snapshots) | Result |
| --- | --- | --- | --- |
| projects-create | 2 min 10 s | 8 s | pass, pass |
| projects-archive | 1 min 40 s | fail (harness) | pass, then a false red |
| orgs-preferences-persist | 20 s | not rerun | pass |
| editor-import-and-edit | 2 min | not rerun | pass after one retry of the typing step |

Cold time is mostly the agent thinking between commands, not the browser.
The browser side of every step was under a second.

## What a snapshot costs

Measured on the editor page with `sample.md` open, seven cells:

| Snapshot | Characters | Rough tokens |
| --- | --- | --- |
| full tree | 9,910 | 2,500 |
| interactive only (`-i`) | 5,891 | 1,500 |
| one editor row (`-i -s "[data-cell-id]:first-of-type"`) | 1,388 | 350 |
| org Projects page (`-i -c`) | 2,957 | 750 |

A cold four-story run took about 40 snapshots. Call it 40k tokens of page
reading plus the agent's own reasoning. A warm run needs almost none.

## The false red

The warm archive run reported failure. The app was fine. Two harness misses:

1. `find role link click --name "Projects"` returned "Element not found"
   although the snapshot listed `link "Projects"`. The same happened for the
   `Archived` link and for the dialog checkbox. `find role button` worked
   every time; `find text` also failed on the same links. A CSS selector and
   a snapshot ref both worked. The links are an icon plus text inside a
   clickable wrapper, which may be what trips the locator.
2. `wait --text "<project title>"` passed while still on the overview page,
   because the title is the page heading. The step "verified in list" was
   never verified.

Both are exactly Ryder's point: get the harness green on a known-good build
before a red is allowed to mean anything. Each story now carries a note so
the next run avoids the trap.

## What the agent could do that Playwright cannot

- Recover from a wrong assumption mid-run: the language pickers looked like
  dropdowns, did not open on click, and the agent tried typing a code instead.
- Notice that the "Back to <title>" history button is not a table row.
- Explain a failure in words with a screenshot, without anyone writing a
  reporter.

## What it cannot replace

- Exact assertions on races and ordering. The throttled concurrent-edit smoke
  and the ten-client 3G simulation stay in Playwright.
- A merge gate. Two of six warm-run steps misfired for harness reasons with
  no app change. That flake rate is fine for a scout and unacceptable for a
  gate.

## Accessibility notes the app might want

Nothing blocked the agent, which is a good sign for the app's labelling.
Small things:

- The sidebar file rows are `generic` wrappers with a button inside; the
  wrapper carries the file name and the button repeats it. Harmless, doubles
  the snapshot.
- The `More actions` header button has no project name in its label, while
  the table's row menus do (`More actions for <title>`). Either is fine; the
  agent found both.
